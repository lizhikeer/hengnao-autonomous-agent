## 一、一句话总结

把「内网服务 → 恒脑 SaaS」的接入方式，从**不可用的临时隧道**换成了**固定域名 + 自控中转的稳定链路**，同时补齐了数据入库与检测线索两层底座；应用层仍停在 Mock 数据，等 `@chensz-u` 接线。

## 二、链路变更（本次最大的结构性调整）

### 2.1 三代链路演进

| 代次 | 方案 | 结果 | 弃用原因 |
| :--- | :--- | :--- | :--- |
| 第一代（W1 初） | `cloudflared` 快速隧道（`*.trycloudflare.com`） | 能用 | 每次重启域名就变，恒脑平台 5 个能力项的 URL 要跟着改；不可作为交付通道 |
| 第二代（W1 末） | natfrp 免费节点（日本 `frp-fly.com`） | HTTP 能用，HTTPS 需 DNS | 免费节点 10 Mbps 且工作连接频繁被重置，实测约 **1/4 请求返回 502**；国内访问日本节点延迟高 |
| **第三代（当前）** | **朋友的国内中转服务器 `125.112.0.13`（frps）+ NAS 上独立 frpc + 本地 Caddy 终止 TLS** | **稳定，平台已实测通过** | — |

### 2.2 当前链路

```
恒脑 SaaS 云端（仅 IPv4）
   │  HTTPS，Let's Encrypt 证书，严格校验通过
   ▼
https://seclog.91666.icu:18443
   │
   ▼  公网 IPv4 125.112.0.13:18443（frps，国内家宽 + DDNS）
   │  TCP 隧道（token + TLS）
   ▼
NAS（kekeshenla，内网 192.168.0.2）上的 frpc-seclog.service
   │
   ▼  127.0.0.1:18443（seclog-caddy，本地终止 TLS）
   │
   ▼  127.0.0.1:18000（SecLog FastAPI / MCP）
```

关键点：**TLS 在 NAS 本地终止**，中转机只做四层转发，看不到明文；证书私钥不出内网。

### 2.3 为什么必须走 IPv4 中转

NAS 有公网 **IPv6**（`91666.icu` 只有 AAAA 记录），但恒脑 SaaS 云端**没有 IPv6 路由**。
这不是配置问题，是平台侧网络能力的硬约束，所以必须有一台有公网 IPv4 的机器做跳板。

### 2.4 已排除的方案（避免重复讨论）

| 方案 | 排除原因 |
| :--- | :--- |
| 给 `91666.icu` 加 A 记录直连 NAS | NAS 没有公网 IPv4，A 记录无处可指 |
| 把 `seclog` 做成 CNAME 指向中转 DDNS 域名 | 证书续期走 acme.sh 的 `dns_dp`（DNS-01），`_acme-challenge` 子域挂在 CNAME 父节点下，部分递归解析器会解析失败，等于拿「IP 跟随」换「续期失败」 |
| 使用平台要求的 443 标准端口 | 中转机的 80/443 已被 frps 分配给朋友的业务，要复用需对方改配置并做 SNI 分流，改动面大、协调成本高 |
| 继续用 cloudflared | 见上表 |

## 六、检测层变更（本次技术含量最高的部分）

### 6.1 问题

老项目 `RuleEngine` 按**业务动作语义**判定（`action == "login"`、`action == "api_call"`、`_is_download_or_export`），
而统一 Schema 存的是**协议事实**（`GET`/`POST`/`ssh`/`tcp`）。**不做映射，一条规则都命中不了。**

### 6.2 解决：两层规则

| 层 | 文件 | 职责 |
| :--- | :--- | :--- |
| 适配层 | `src/detection/from_full_chain.py` | 统一 Schema → `NormalizedLog`，动作语义从 URI 推断（`/admin/login.php` → `login`，401 → `fail`） |
| 老规则层 | `src/detection/rules.py`（未改动） | 爆破、敏感资源、API 高频、下载外带、权限变更、横向移动 |
| 补充规则层 | `src/detection/full_chain_rules.py`（新增） | 只补老规则不覆盖的 6 类：扫描探测、SQLi、XSS、路径遍历、恶意上传、webshell、可疑外连 |
| 入口 | `scripts/detect_clues.py` | 合并两层输出 |

设计约束：`attack_stage_hint` 只透传不参与判定，避免标注数据反向污染检测结果；补充规则的风险定级用 `risk_component_overrides`，不动团队共享的 `config/risk-scoring-v1.json`。

### 6.3 实测（`CHAIN-001`，61 条日志）

```
线索 8 条（老规则 2 / 补充规则 6）
  brute_force 2 · Malicious_Upload 2 · Webshell_Access 2 · Scanning_Probe 1 · SQL_Injection 1
风险分布：high 2 / medium 5 / low 1
```

XSS、路径遍历、可疑外连三条规则已实现，但**当前样本无对应流量**，尚未真实验证。

## 十、给上游的三个决策问题与本周中期纠偏裁定（主 Agent 决议）

1. **中转要不要自建？**
   - *问题*：现在依赖朋友的机器（`125.112.0.13`），好处是零成本、已跑通；风险是对方下线/换机即断。是否值得投入一台自己的低配云服务器？
   - **【主 Agent 裁定】**：**W2~W3 保持使用现有国内 IPv4 中转（`125.112.0.13` + 5 分钟 DDNS 同步 `seclog.91666.icu`），暂不额外采购新云主机**。当前链路延迟低、TLS 在 NAS 本地终止安全可控；仅当后续出现连续断连影响 W4 端到端联调时，再启用百元级轻量云备份方案。

2. **18443 非标端口要不要继续用？**
   - *问题*：平台已实测接受。改 443 需要朋友的 frps 做 SNI 分流，协调成本高。
   - **【主 Agent 裁定】**：**正式锁定 `https://seclog.91666.icu:18443` 作为全组唯一公网基线，不做 443 端口改造**。严禁在网络穿透层继续消耗额外工时。恒脑平台侧统一配置：REST Base URL 为 `https://seclog.91666.icu:18443`，只读调查 MCP 为 `https://seclog.91666.icu:18443/investigation/`，全量 MCP 为 `https://seclog.91666.icu:18443/mcp/`（**尾部斜杠必填**）。

3. **检测规则的「两层」设计是否要保留？**
   - *问题*：当前是「老规则不动（`rules.py`）+ 补充规则层（`full_chain_rules.py`）+ 上下文降权（`context_builder.py`）」，是否在 W3 合并成单一规则层？
   - **【主 Agent 裁定】**：**保留「老规则 + 补充规则 + 上下文降权」两层架构，不合并进 `rules.py`**。原因：① 保持 `src/detection/rules.py` 零侵入可证明对老项目的原汁原味复用；② `from_full_chain.py` + `full_chain_rules.py` 职责清晰，专门对齐 `@Snowed-night` 制定的 WSTG v4.2 + ATT&CK 7 类攻击枚举；③ 配合 `ContextRegistry` 读取 `config/assets.yaml` 与 `config/maintenance-windows.yaml`，已实测将 `CHAIN-CASE-03` 正常运维误报压降为 `medium`，完全满足 W2 里程碑要求。
