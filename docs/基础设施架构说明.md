## 一、总览

项目只有 **两台常驻机器** 参与线上链路，另有一台已退役的备用机。

```
┌─────────────────────┐        公网 IPv4          ┌──────────────────────┐
│  恒脑 SaaS 云端      │ ───────────────────────► │  中转机（朋友的）      │
│  只有 IPv4 出口      │    HTTPS 18443           │  125.112.0.13:7000   │
└─────────────────────┘                          │  frps + DDNS         │
                                                 └──────────┬───────────┘
                                                            │ frp 隧道
                                                            │ （token + TLS）
                                                 ┌──────────▼───────────┐
                                                 │  NAS「kekeshenla」    │
                                                 │  192.168.0.2         │
                                                 │  无公网 IPv4         │
                                                 │  仅公网 IPv6         │
                                                 │  ┌────────────────┐  │
                                                 │  │ SecLog 全部服务 │  │
                                                 │  └────────────────┘  │
                                                 └──────────────────────┘
```

关键约束：**NAS 没有公网 IPv4**，恒脑云端**没有 IPv6 路由**，两者之间必须有一台双栈机器做跳板——这就是中转机存在的唯一原因。

## 三、网络拓扑与链路

### 3.1 完整链路（当前生效）

```
恒脑 SaaS 云端
  │  HTTPS（Let's Encrypt，TLS 1.2/1.3，证书 SAN 精确匹配）
  ▼
https://seclog.91666.icu:18443
  │  DNS：seclog.91666.icu → A → 125.112.0.13（每 5 分钟由 cron 同步）
  ▼
中转机 125.112.0.13:18443
  │  frps 按端口转发
  ▼
NAS frpc-seclog.service（systemd，Restart=always）
  │  本地转发到 127.0.0.1:18443
  ▼
seclog-caddy（容器，host 网络，只 bind 127.0.0.1）
  │  TLS 在此终止，反向代理
  ▼
seclog-api（容器）127.0.0.1:18000
  │
  ├─► seclog-clickhouse  127.0.0.1:8123 / 9000
  └─► seclog-qdrant      127.0.0.1:6333 / 6334
```

### 3.2 为什么用 `seclog.91666.icu` 而不是中转机自己的 DDNS 域名

证书签在 `seclog.91666.icu` 上，换域名等于换证书。而中转机是家宽动态 IP，如果直接把 A 记录写死，IP 一变就断。

解决方式是 **A 记录跟随**（不是 CNAME）：

```
cron（每 5 分钟）
  → 解析 9188888.cn 的 A 记录
  → 与 seclog.91666.icu 当前 A 记录比对
  → 不一致则调 DNSPod API 更新
```

脚本：`scripts/ops/ddns_sync.py`，凭据复用 acme.sh 已存的 DNSPod token。

**不用 CNAME 的原因**：证书续期走 acme.sh 的 `dns_dp`（DNS-01），需要在 `_acme-challenge.seclog.91666.icu` 建 TXT 记录；父节点是 CNAME 时部分递归解析器会拒绝解析其子域，等于拿「IP 跟随」换「续期失败」。

### 3.3 HTTPS 证书

| 项 | 值 |
| :--- | :--- |
| 签发 | Let's Encrypt ECC，CN=`seclog.91666.icu` |
| 有效期 | 2026-11-12 → 2027-02-10 |
| 续期 | `acme.sh --cron`，每天 03:59 / 09:59 / 15:59 / 21:59，`dns_dp` 方式 |
| 证书路径 | `/etc/caddy-seclog/certs/seclog.91666.icu.{pem,key}`（宿主，600） |
| 加载方式 | Caddyfile 里 `tls` 指令手动指定，**Caddy 不做 ACME** |

续期后需要让 Caddy 重新加载证书，否则仍在用旧的。续期 hook 目前未挂，属于遗留项（见 §9）。

## 八、运维操作

### 8.1 日常

```bash
# 服务状态
docker ps --filter name=seclog
systemctl status frpc-seclog

# 日志
docker logs -f seclog-api
docker logs -f seclog-caddy
journalctl -u frpc-seclog -n 50

# 重启链路（改了 frpc 配置后）
sudo systemctl restart frpc-seclog

# 改代码后重建 API
cd ~/seclog/docker && docker compose --env-file ../.env up -d --build api
```

### 8.2 数据

```bash
# 建表（幂等，改过 sql/ 后必跑）
cd ~/seclog && ./scripts/apply_clickhouse_sql.sh

# 灌日志
python3 scripts/ingest_clickhouse.py --input data/full_chain_logs/normalized/

# 跑检测线索
docker run --rm --user root --network docker_default \
  -v /home/lzk/seclog:/repo -w /repo --env-file .env \
  -e CLICKHOUSE_HOST=clickhouse -e PYTHONPATH=/repo \
  seclog-api:0.1.0 python scripts/detect_clues.py --trace-id CHAIN-001
```

> 宿主机 python3 **没装 pydantic**，脚本里的 Python 代码要跑在 `seclog-api` 容器里。
> 容器内 `.env` 是 600 且属主为 `lzk`，需要 `--user root` 才能读。

### 8.3 证书

```bash
# 手动续期
~/.acme.sh/acme.sh --renew -d seclog.91666.icu --force

# 续完把新证书复制到 Caddy 目录并重载容器
docker restart seclog-caddy
```

### 8.4 镜像拉取（国内网络）

`docker pull` 直连 Docker Hub 极慢或超时。可用 `crane` 走国内镜像源：

```bash
cd /vol4/seclog/bin
./crane pull --platform linux/amd64 docker.m.daocloud.io/<image>:<tag> /tmp/x.tar
docker load -i /tmp/x.tar
```

可用源：`docker.m.daocloud.io`（有白名单限制）、`docker.1ms.run`（较全但慢）。

## 九、故障排查

### 9.1 平台报"网络不可达"

按顺序查：

1. **DNS**：`dig +short A seclog.91666.icu` 应返回中转机当前 IP
2. **中转机**：`ping 125.112.0.13`（可能禁 ICMP，改测 `nc -z 125.112.0.13 7000`）
3. **隧道**：`systemctl status frpc-seclog`，日志里应有 `start proxy success`
4. **本地 Caddy**：`curl -sS https://seclog.91666.icu:18443/health -k`（先 `-k` 排除证书问题）
5. **后端**：`curl -sS http://127.0.0.1:18000/health`

### 9.2 证书报错

- 检查 `openssl s_client -connect seclog.91666.icu:18443 -servername seclog.91666.icu` 看证书是否过期
- 过期就手动续期（§8.3）并重启 Caddy

### 9.3 全家桶都正常但平台调不通

平台侧可能没配端口或配了错误路径。当前平台已实测接受 `18443`；MCP 必须 `/mcp/`。

## 十、已知限制

| 限制 | 影响 | 缓解 |
| :--- | :--- | :--- |
| 中转机是朋友的、家宽 | 单点依赖；对方下线/换机即断；上行带宽有限 | DDNS + 定期检查；W3 评估自建 |
| 非标端口 18443 | 平台策略若收紧需改 443 | 改为 443 需朋友的 frps 做 SNI 分流，成本高 |
| NAS 仅 7.7 G 内存 | 服务多了会 OOM | 各容器已设内存上限，加服务前先看 `docker stats` |
| 宿主机无 pydantic | 运维脚本必须跑在容器里 | 见 §8.2 |
| 证书续期无 hook | 续期后不自动 reload，可能仍用旧证书 | 待补 hook（`--reloadcmd "docker restart seclog-caddy"`） |
| `seclog-frpc` 容器仍在线 | 占用 natfrp 隧道名额，且与主链路域名冲突 | 待确认后下线 |
| 明文 18000 | —— | **已关闭**，仅本地可达 |
