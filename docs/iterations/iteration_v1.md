## 3.3 根因定位分析

| 根因类别 | 具体定位 | 对应案例 |
| --- | --- | --- |
| 知识检索不可用 | V1 环境缺少混合检索依赖，6 次 `search_knowledge` 为 `backend_unavailable`，组合攻击阶段与知识卡未能参与判定 | 01、02、04、05、06、08 |
| 证据选择缺少阶段完整性 | 能查到日志，但倾向截取显著攻击片段，未稳定覆盖“成功后影响、会话复用、越权读取、正常登出”等闭环证据 | 01、03、04、05、10 |
| 授权否决与恶意判定耦合 | “无法批准为正常”被直接转成弃权；同时忽略爆破成功、同源失败转成功、周期外连等行为证据 | 06、08、10 |
| 正常场景来源归一化缺失 | 正常结论使用 `attacker_ip=unknown`，没有回填已确认的运维/扫描来源，导致 IP 要素不匹配 | 03、09 |
| 主分类冲突处理不足 | 多类行为同时命中时，时序与主攻击链选择不稳定，CASE-02 选择目录遍历而非 Webshell + C2 主链 | 02 |
| 评分器缩写解析缺陷（非 Agent 根因） | 旧分词器将连续大写缩写拆开，造成 CASE-04、05 的历史误扣分；已由 `7ae6463` 修复 | 04、05（仅旧报告） |

CASE-06、08、10 的关键共性不是“没有证据”：前两例证据召回已为 100%，而是控制器把授权核对失败作为阻断结论的条件，没有用行为模式完成恶意/正常分流。因此 V2 的修复重点是行为规则与知识卡驱动调查，而不是简单增加引用数量。
