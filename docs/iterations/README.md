| 标识项 | 含义 | 记录示例 |
| --- | --- | --- |
| `model_rev` | 基座模型标识（模型名称 + 具体版本 / 快照） | `deepseek-v4 / 2026-10-20 snapshot` |
| `kb_rev` | 知识库版本（知识卡片集合的版本号或 commit hash） | `kb-20261101 (commit a1b2c3d)` |
| `case_rev` | 案例库版本（错题 / 纠错案例卡的版本号） | `cases-20261101 (commit e4f5g6h)` |

补充固定项：评测集版本 `eval_rev`、评测脚本版本 `scorer_rev`、运行参数（温度 / 最大轮次 / 随机种子）。

## 3. 单轮迭代记录模板（五要素，逐轮复制填写）

每轮迭代必须完整填写以下五节，**五节缺一不可**。建议每轮单独建文件 `docs/iterations/iteration_v{N}.md`，并在本文件第 2 节表格中登记链接。

### 3.1 迭代版本号与变更时间戳

| 字段 | 内容 |
| --- | --- |
| 迭代版本号 | 例如 `V2` |
| 变更时间戳 | `2026-11-05 20:00 (UTC+8)` |
| 基座模型标识 `model_rev` | 例如 `deepseek-v4 / 2026-10-20` |
| 知识库版本 `kb_rev` | 例如 `kb-20261101` |
| 案例库版本 `case_rev` | 例如 `cases-20261101` |
| Prompt 版本 `prompt_rev` | 例如 `prompt-v2.1` |
| 评测集版本 `eval_rev` | 例如 `eval-20261101（正常 30 例 / 恶意 40 例）` |
| 本轮变更范围摘要 | 3～5 条，写清「改了哪个文件 / 哪段 Prompt / 哪张知识卡」 |

### 3.2 发现的具体问题现象与失败案例编号

先用评测集跑出失败清单，再逐条记录现象；**不允许只写「效果不好」这类模糊结论**。

| 失败案例编号 | 场景描述（输入要点） | 期望输出 | 实际输出 | 失败类型 | 是否已转为回归用例 |
| --- | --- | --- | --- | --- | --- |
| EVAL-CHAIN-001 | 先爆破后 SQL 注入 | 恶意 / HIGH / block_ip | 判为正常业务 | 攻击召回缺失 | 是 |
| EVAL-CHAIN-007 | … | … | … | … | … |

失败类型建议使用以下受控词表（便于后续统计归因）：

- `漏查证据`：Agent 未检索关键日志（如漏查 Zeek 外连日志）
- `误判类型`：把正常运维误判为爆破 / 扫描等
- `伪造证据`：编造不存在的证据日志 ID 或行号
- `处置不当`：建议动作与风险等级不匹配（如 LOW 直接封禁）
- `越权调用`：调用未授权工具或越过审批直接执行处置
- `结论不可复现`：两次运行结论不一致（随机性过高）

### 3.3 根因定位分析

每条失败案例都要定位到唯一根因层级，禁止用「模型能力不足」一句概括。

| 根因类别 | 判定标准 | 对应失败案例编号 |
| --- | --- | --- |
| Prompt 缺少约束 | 提示词未要求核对外连日志 / 未要求引用证据 ID | 待填写 |
| 知识卡缺失 | 知识库无该类攻击链的判定要点（如爆破后注入的组合特征） | 待填写 |
| 全链路日志字段未对齐 | 解析层字段名与知识卡、Prompt 描述不一致，导致检索命中失败 | 待填写 |
| 工具调用策略缺陷 | 查询顺序 / 轮次上限设置不合理，关键日志未被检索 | 待填写 |
| 幻觉 / 证据编造 | 模型输出不存在的日志 ID 或篡改字段值 | 待填写 |

## 4. 评测指标定义与统计口径

所有指标均由 `scorer` 脚本基于评测集标注（`ground_truth`）自动计算，**不允许人工挑选样本或手工修正结果**。

| 指标 | 计算公式 | 说明 |
| --- | --- | --- |
| 诊断准确率 | `(TP + TN) / 总样本数` | 恶意 / 正常二分类整体正确率 |
| 攻击召回率 | `TP / (TP + FN)` | 恶意样本中被正确判为恶意的比例，漏报代价最高 |
| 证据支持率 | `证据可回溯案例数 / 输出结论案例数` | 结论引用的日志 ID 必须真实存在且与结论语义一致 |
| 处置正确率 | `动作一致案例数 / 恶意案例数` | 允许配置「可接受动作集合」，如 `block_ip` 与 `isolate_host` 可视为等价 |
| 正常业务误杀率 | `FP / 正常业务样本数` | 误杀会直接影响业务可用性，需单独监控 |

计算前置约定：

1. 评测集必须包含正常业务样本（建议不少于 30 例），否则误杀率无意义；
2. 恶意样本需按攻击类型分层抽样，保证各类攻击（爆破、注入、横向移动、数据外传等）均有覆盖；
3. 同一轮的所有实验固定 `temperature` 与随机种子；若必须使用非零温度，需跑 3 次取均值并记录方差；
4. 指标对比只允许使用同一 `eval_rev`，换评测集必须重跑基线，并在台账中注明。

## 5. 交付与提交规范

1. 每轮迭代完成后，新增 `docs/iterations/iteration_v{N}.md`，并在本文件第 2 节登记；
2. 每个优化措施必须对应一次可查的 commit，台账中登记 commit hash；
3. 评测原始输出（JSON / CSV）放入 `docs/iterations/artifacts/v{N}/`，与台账同轮提交；
4. 本轮未修复的问题必须写入「遗留问题」小节，明确责任人与下一轮计划动作；
5. PR 描述中必须贴出本轮指标对比表，Reviewer 需核对台账与评测产物是否一致。
